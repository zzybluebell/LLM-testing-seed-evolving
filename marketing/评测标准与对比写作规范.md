# Doubao-Seed-Evolving 宣发：评测标准与对比写作规范

> v0.1 · 2026-09-10 23:55 · 目的：宣发稿里每一句"比谁强"都能回溯到一个 run_id、一个 check 编号或一个 telemetry 字段。凡是本文件没有列出证据来源的主张，不写进稿子。

## 1. 三条硬规则

1. **只写脚本判定的结果。** 13 项验收由 `scripts/check.py` 产出，不做人工加分减分；模型产物不修改。
2. **每个数字带四个标签**：模型 ID、提示词版本（vague/detailed）、轮次 n、测试日期。Evolving 是滚动 ID，缺日期的数字没有意义。
3. **对手的短板先核实是"模型"还是"环境"。** 例：DeepSeek/GLM 在方舟不支持图片输入是端点限制，不能写成"看不懂截图"；它们用 OCR 补救后 c13 照样通过。

## 3. 维度指标：从 telemetry.json / cost.json / live.jsonl 取

| 指标 | 字段 | 写法 |
|---|---|---|
| 耗时 | `model_s`（模型时间）、`wall_s` | 对外用 model_s，墙上时间受人工操作影响 |
| 轮数 / 工具调用 | `turns`、`tool_calls` | 越少越"精简"，但要和得分一起看 |
| 出字速度 | `total_output_tokens / model_s` | 单位 tok/s，跨模型最直观 |
| 单轮延迟 | live.jsonl 相邻 turn 的 elapsed_s 差 | 报中位数和最大值 |
| 成本 | `cost_native`（人民币）、`cost_usd`、每通过一项的成本 | Opus 按 API 牌价折算，注明"订阅制等价" |
| 缓存命中 | `cache_read / (input + cache_read)` | 长任务成本主要看这里 |
| 长任务稳定性 | `babysit`=0、`step_limit_hit`=False、`compaction_events`=0、`timed_out`=False | 四个都要写 |
| 多模态 | `image_reads`、`image_reads_blocked`、会话里 `image/png` 块数 | 区分"原生读图"和"OCR 补救" |
| 协议兼容 | `thinking_signature_seen` | 三家国产里只有 Evolving 为 True |

## 4. 公平性声明（稿子里必须保留）

- Claude Code 是 Anthropic 自家 harness，Opus 5 是天花板参照，不是公平对手。
- DeepSeek-V4-Pro、GLM-5.2 的方舟端点不接受图片输入（400），harness 用 hook 拦截 Read 并提示可用 tesseract OCR；两者都用了 OCR，因此 c13 对它们不是不可能。
- 40 分钟硬超时已关闭（2026-09-10 决定），运行到模型自行停止或 60 轮上限；耗时对比因此是"自然完成时间"。
- 目前所有数据都是 n=1，中位数、方差都还没有。写"稳定"之前至少要 n=3。
- Opus 由用户在自己的 Claude Code 里手动跑，其余由 `run_all.py` 在 `env -i` 隔离环境里跑；两者 Claude Code 版本一致（2.1.231），effort 都是 high。

## 7. 措辞规则

- 不用"最强""碾压""全面领先"。用"在 X 项验收里通过 Y 项，对比 Z"。
- 每个百分比、每个金额后面括号写 run_id，例：13/13（evolving/detailed/1，2026-09-10）。
- 对手失分要写原因，不只写分数。读者能复现的失分才有说服力。
- Evolving 的短板（速度）写在正文而不是脚注；写了短板，优点才可信。
- 周更曲线（Phase 6）没跑之前，不写"每周变强"，只写"同一 ID 可按周复测"。
